#8.2 CTG Document Structure and State Machine

You can model CPE/CTG in your ERP directly from the WSCPE web‑service schema: the CPE “document” is essentially the `autorizarCPEAutomotor` / `autorizarCPEFerroviaria` solicitud plus a small set of extra fields added by ARCA (CTG, CPE number, states, timestamps, etc.). Below I map the main fields, states, and roles so you can design tables and a state engine aligned with AFIP/ARCA 2.0.x (2023–2025) and recent SISA rules (2026).[^1][^2][^3][^4][^5][^6]

> Important limitation: the official manuals define hundreds of simple/complex types and all multiplicities. Practically, you will still need to keep the AFIP WSDL and the “Tipos de Datos Simples/Complejos” tables as the canonical reference for edge‑case fields and future changes. What follows focuses on the grain CPE Automotor path, which is the core of CTG usage.[^1]

***

## CPE/CTG lifecycle in practice

For grains CPE Automotor, the operational phases are:[^3][^7][^1]

1. **Creation/Authorization (Emisión)** – Origin operator calls `autorizarCPEAutomotor`; ARCA returns CTG, CPE number and initial state (usually Activa).
2. **Transit** – Truck travels with printed/QR CPE; optional contingencies or desvío/regreso can be reported via WS methods.[^8][^1]
3. **Arrival** – Destination (or its system) calls `confirmarArriboCPE`, which only changes state, not business data.[^9][^1]
4. **Unloading / Descarga** – Destination calls `descargadoDestinoCPE` and then `confirmacionDefinitivaCPEAutomotor` sending final gross/tare; ARCA computes net and closes the CTG.[^10][^9]
5. **Closure / Exceptions** – Anulación, rechazo, regreso a origen, contingencias and vencimiento follow side paths in the state machine (see below).[^11][^12][^1]

These phases map well to separate write‑events in your ERP: **Create → Arrive → Unload → Close**, with intermediate events for **Cancel/Reject/Divert/Contingency**.

***

## Creation‑phase fields (origin operator)

The main creation payload for grains automotor is `autorizarCPEAutomotor.solicitud`, which groups fields into `cabecera`, `origen`, `intervinientes`, `datosCarga`, `destino`, `destinatario`, `transporte` and `observaciones`.[^4][^13]

### Header and core IDs

These drive uniqueness and ARCA numbering:


| Field (logical) | WS path | Type / max len | Mandatory | Values / notes | Filled by |
| :-- | :-- | :-- | :-- | :-- | :-- |
| CPE type | `cabecera.tipoCP` | `short` (3) | Yes | AFIP type codes, e.g. 74/75/274/284… (includes flete corto).[^1][^8][^10] | Origin operator (solicitante) |
| Soliciting CUIT | `cabecera.cuitSolicitante` | CUIT, 11 digits | Yes | Must be SISA‑registered producer or grain operator with active plants.[^1][^3][^14] | Remitente comercial / productor |
| Branch (Sucursal) | `cabecera.sucursal` | int | Yes | Links to your ERP POS/branch; used in ARCA to compute last order.[^1] | Origin operator |
| Order number | `cabecera.nroOrden` | int | Yes | Local sequential within sucursal; used to track last successful CPE in error recovery.[^1] | Origin operator |

AFIP simple type table defines CUIT as 11‑digit numeric `^\d{11}$`; order and sucursal are positive integers.[^1]

### Origin (operator and producer)

Origin is split between the **commercial operator’s plant** and the **producer’s field**, with optional GPS:[^13][^15][^4]


| Field | WS path | Type / len | Mand. | Notes | Filled by |
| :-- | :-- | :-- | :-- | :-- | :-- |

| Origin plant code | `origen.operador.planta` | int | Yes | Plant registered in SISA for the operator CUIT.[^1][^3] | Origin operator |
| Producer province | `origen.productor.codProvincia` | int | Yes if “campo” | SISA locality for field when origin is a field.[^7] | Origin operator / producer |
| Producer locality | `origen.productor.codLocalidad` | int | Yes if “campo” | As above. | Origin operator / producer |
| RENSPA number | `origen.productor.nroRenspa` | string | Optional | Farm registry id; some flows (emisión en destino, CPEDG) use RENSPA strongly.[^1] | Producer / origin |
| GPS latitude deg/min/sec | `origen.productor.coordenadasGPS.latitud.{grados,minutos,segundos}` | string (2–3 chars each) | Optional | Textual representation; AFIP simple types constrain numeric ranges.[^1] | Origin operator |
| GPS longitude deg/min/sec | `…longitud.{grados,minutos,segundos}` | string | Optional | Same.[^1] | Origin operator |
| Georeferenced location | `…ubicacionGeoreferencial` | string (~100) | Optional | Free‑text place label; simple type defined but not heavily constrained.[^4][^1] | Origin operator |

Flags about whether the **solicitante is the producer**:


| Field | WS path | Type | Mand. | Meaning |
| :-- | :-- | :-- | :-- | :-- |
| Producer pickup? | `correspondeRetiroProductor` | boolean | Yes | True when producer withdraws grain from operator plant.[^4][^16] |
| Solicitor is field? | `esSolicitanteCampo` | boolean | Yes | True if the CUIT solicitante is a field holder (producer).[^4][^15] |
| Producer remitente CUIT | `retiroProductor.cuitRemitenteComercialProductor` | CUIT | Cond. | Used in “remitente comercial productor” interviniente when picking up from plant.[^4][^16] |

The **intervinientes** group represents all commercial roles:[^16][^4]


| Field | WS path | Type | Mand. | Valid values / role | Typical actor |

AFIP’s “intervinientes” help page explains when each CUIT should be populated; from a DB view, treat them as nullable FKs to your `Party` table keyed by CUIT.[^16]

### Cargo / grain data

Grain data is compact; type codes and harvest are heavily validated:[^10][^4][^13]


| Field | WS path | Type | Mand. | Notes | Filled by |
| :-- | :-- | :-- | :-- | :-- | :-- |
| Grain code | `datosCarga.codGrano` | numeric (2) | Yes | AFIP grain code catalog; Finnegans doc lists mappings, e.g. 19=Maíz, 23=Soja, 15=Trigo Pan etc.[^10] | Origin operator |
| Crop (cosecha) | `datosCarga.cosecha` | numeric (4) | Yes | Simple type “Cosecha”; AFIP uses 4‑digit number, often printed as `20-21` but transmitted as `2021`.[^1][^10] | Origin operator |
| Estimated gross weight | `datosCarga.pesoBruto` | int | Yes | In kg; must be consistent with SISA stock, CTG rules and vehicle limits.[^4][^3][^17] | Origin operator |
| Estimated tare | `datosCarga.pesoTara` | int | Yes | Truck+trailer tare; used to compute estimated net.[^4] | Origin operator |

AFIP simple‑type table defines `CodigoGrano` as 2‑digit numeric and `Cosecha` as 4‑digit numeric. In practice, ERP tables usually store: `grain_code`, `harvest_code`, `est_gross_kg`, `est_tare_kg`.[^1]

### Destination \& destinatario

Destination is the **physical plant or field**, while **destinatario** is the commercial receiver.[^7][^4][^16]


| Field | WS path | Type | Mand. | Notes | Filled by |
| :-- | :-- | :-- | :-- | :-- | :-- |
| Dest CUIT (operador) | `destino.cuit` | CUIT | Yes | Operator of destination plant or field; must be active in SISA and plant active in 2026 regime.[^3][^5][^6] | Remitente / origin system |
| Destination is field? | `destino.esDestinoCampo` | boolean | Yes | Controls whether SISA field localities or plant list is shown.[^7] | Origin |
| Dest province | `destino.codProvincia` | int | Yes | AFIP province.[^1] | Origin |
| Dest locality | `destino.codLocalidad` | int | Yes | `ConsultarLocalidadesPorProvincia`.[^1] | Origin |
| Dest plant | `destino.planta` | int | Yes if not campo | Must be one of the CUIT’s SISA plants (and “Activa” under 2026 rules).[^3][^5][^6] | Origin |
| Destinatario CUIT | `destinatario.cuit` | CUIT | Yes | Commercial recipient of grain (may differ from plant owner).[^16] | Remitente |

For DB design: separate **DestinationPlant** (CUIT+planta+locality) and **DestinatarioParty** (CUIT) even if in most domestic flows they match.

### Transport: truck and driver

Truck and driver are under `transporte` and are central to CTG validation:[^15][^4][^13][^7]


| Field | WS path | Type / len | Mand. | Notes | Filled by |
| :-- | :-- | :-- | :-- | :-- | :-- |
| Transporter CUIT | `transporte.cuitTransportista` | CUIT | Yes | Carrier must be registered (e.g. RUTA) and OK in SISA/ARCA risk profile.[^4][^14] | Origin (via freight contract) |
| License plates | `transporte.dominio[]` | array of strings | At least 1 | Each simple type “DominioCamion”: 6–7 alphanumeric chars (patente). Multiple for truck+trailer.[^4][^1] | Origin / carrier |
| Departure datetime | `transporte.fechaHoraPartida` | datetime | Yes | AFIP uses `YYYY-MM-DDThh:mm:ss` or `aaaammddhhmm`; UI asks for “Fecha y hora de partida”.[^4][^18][^7] | Origin |
| Km to travel | `transporte.kmRecorrer` | int | Yes | Used to compute validity window (CPE automotor ≈ 5 days, ferro 30 days) and tariff reference.[^3][^19][^18] | Origin |
| Turn / slot code | `transporte.codigoTurno` | string (≤30) | Optional | Required for port/plant scheduling systems when cupo is enforced.[^18][^1] | Origin or plant |
| Driver CUIT | `transporte.cuitChofer` | CUIT | Yes | Driver must exist in transporter’s registry; captured in step “Datos de la carga” UI.[^4][^7] | Origin / carrier |
| Agreed tariff | `transporte.tarifa` | decimal | Optional (but recommended) | Tarifa reference is calculated by ARCA; actual agreed tariff can be reported.[^7][^20] | Origin / carrier |
| Freight payer CUIT | `transporte.cuitPagadorFlete` | CUIT | Optional | Who pays freight (producer, buyer, third‑party).[^4][^7] | Remitente |
| Freight intermediary CUIT | `transporte.cuitIntermediarioFlete` | CUIT | Optional | When there is an intermediary de flete in the model.[^4][^21] | Intermediario de flete |
| Fumigated? | `transporte.mercaderiaFumigada` | boolean | Optional | Indicates if cargo is fumigated; flagged in UI.[^4][^7] | Origin |

AFIP simple types constrain `codigoTurno` to a 30‑char string and domain to 6–7 alphanumerics.[^1]

### Miscellaneous

| Field | WS path | Type | Mand. | Notes |
| :-- | :-- | :-- | :-- | :-- |
| Observations | `observaciones` | string (up to ≈2000 chars) | Optional | Free text; one per CPE.[^1][^4] |

All of the above are **captured at creation** and sent in a **single call** to `autorizarCPEAutomotor`; ARCA returns CTG, CPE number and sets the initial state.[^4][^10][^1]

## Fields at confirmation, arrival, unloading and ARCA‑managed fields

### Fields at “confirmation” by destination

The destination’s main actions are **Confirm Arribo**, **Descargado en Destino**, and **Confirmación Definitiva**. The WS methods are:[^12][^9][^1]

- `confirmarArriboCPE` – identifies CPE by type/sucursal/nroOrden or CTG and **only changes the state to CF (Activa con confirmación de arribo)**; ARCA stamps an internal arrival timestamp.[^9][^1]
- `descargadoDestinoCPE` – marks state DD (Descargado en destino); for grains, it is mostly a state flag that enables definitive confirmation.[^11][^12][^1]
- `confirmacionDefinitivaCPEAutomotor` – receives **final gross and tare at destination** and closes the CTG.[^9]

From Calipso’s WSCPE integration, the definitive confirmation signature is effectively:[^9]

- Input: `cuitSolicitante` (destination CUIT, acting as “solicitante” for this event), CPE identification, `pesoBrutoDescarga`, `pesoTaraDescarga`.
- Effect: ARCA computes net, mermas and updates state CN (Confirmada) and DD as appropriate.[^9][^1]

So, **new business fields introduced post‑creation** are:


| Phase | Logical field | Where it lives | Who sets | Notes |
| :-- | :-- | :-- | :-- | :-- |
| Arribo | Arrival datetime | In ARCA, exposed via `ConsultarCPEAutomotor` | Destination | Implicit; you only store it from the consult response. |
| Descarga | “Descargado en destino” flag | State DD | Destination | No extra payload, just the act of descarga.[^12][^11] |
| Descarga | Final gross at destination | `pesoBrutoDescarga` | Destination weighbridge | Sent in Confirmación Definitiva.[^9] |
| Descarga | Final tare at destination | `pesoTaraDescarga` | Destination | Sent in Confirmación Definitiva.[^9] |
| Descarga | Net and loss (mermas) | Derived in ARCA | Auto | Calculated and visible in consult / certificates.[^10] |

### Fields set automatically by ARCA (system‑generated)

Key ARCA‑managed fields you should model as **read‑only** in your ERP:[^19][^22][^1]


| Field | Meaning / source |
| :-- | :-- |
| CTG (Código de Trazabilidad de Granos) | 12‑digit numeric code; generated per authorized CPE; BCR labs uses it as the unique id in lab files.[^22][^17] |
| CPE number | 13‑digit document number; format \#\#\#\#1‑\#\#\#\#\#\#\#1 (5+8 digits) per Finnegans and BCR labs documentation.[^10][^22] |
| State code | One of AC, AN, BR, CF, CN, CO, DE, RE, PA, AP, DD, PE, IN, PO.[^2][^10] |
| Validity window | For grain CPE automotor, max 5 days; for ferro, 30 days; derived from emission datetime and km to travel.[^3][^19] |
| QR + barcode | Encoded with origin/destination and control data; generated with each authorization and accessible as PDF binary in responses.[^3][^23][^24] |
| PDF representation | Many WSCPE methods return a `pdf` field (base64) with printable CPE; binary only, not part of logical schema.[^1][^24] |
| Error \& validation codes | Business validations, reasons for rejection/anulation, etc., defined in manual annexes and error code tables.[^1] |

In your schema, treat **CTG and CPE number** as separate keys: CTG is the primary tracking code in CTG regulations, while CPE number is the tax document number printed on the form.[^17][^22]

## State machine

### States and meanings

AFIP/ARCA define the following states for CPE (all modalities):[^25][^2][^26][^10]


| Code | Label | Meaning (grains context) |
| :-- | :-- | :-- |
| BR | Borrador | Draft in UI/ERP, **not yet sent** to ARCA (local state only). |
| PE | Pendiente de emisión | Pending emission; used mainly in Derived/Ductos and “emisión en destino”.[^1] |
| PA | Pendiente de Aceptación por el Productor | CPE created by another operator (e.g. acopiador, flete corto) awaiting producer acceptance.[^2][^10][^27] |
| PO | Pendiente de Aceptación por el Origen | Similar, pending acceptance by origin plant operator. |
| AC | Activa | Authorized CPE, truck can load and travel.[^2][^3] |
| CO | Activa con contingencia | Active with open contingency (e.g. IT issues, route incidents).[^2][^1] |
| CF | Activa con confirmación de arribo | Arrival confirmed at destination; still pending unloading or definitive confirmation.[^2][^10] |
| DD | Descargado en destino | Unloading done; used prior to definitive confirmation or in some CPEDG flows as a way to free the truck.[^2][^11] |
| CN | Confirmada | Definitive confirmation completed (weights closed, CTG finalized).[^2][^9] |
| RE | Rechazada | Grain rejected at destination; may trigger regreso a origen or new RT CPE.[^10][^11] |
| AN | Anulada | Cancelled by origin/producer before use (AP) or via standard anulación flow.[^2] |
| AP | Anulación por el Productor | Special cancellation path initiated by producer (linked to PA).[^2] |
| DE | Desactivada | Deactivated, typically after certain error flows or regulatory actions; not usable anymore.[^2] |
| IN | Inactiva | Inactive; used rarely for administrative deactivation. |

“Vencida” (expired) is **not a separate code** in WSCPE; it is a **derived condition** when the current date/time is beyond the validity window (5 or 30 days) for a still‑active CPE. Many UIs and B2B docs refer to “CPE vencida”, but the underlying state remains AC/CF/CO/PE with an expired timestamp.[^3][^19][^11]

### Main transitions, triggers and actors

The exact diagrams for grains are in WSCPE Manual 2.0.x section 2.7.2 “Diagramas de estados – Granos”; below is a practical summary for automotor CPE:[^2][^10][^1][^9]


| From → To | Trigger / method | Who can trigger | Notes |
| :-- | :-- | :-- | :-- |
| BR → AC | `autorizarCPEAutomotor` successful | Remitente comercial / producer (CUIT solicitante) | In standard flows CPE goes directly to AC.[^4][^3] |
| BR → PE | `autorizarCPE…` for “emisión en destino” / derived flows | Operator creating CPEDG or emission‑in‑destino | Later must be accepted to become AC.[^1][^28] |
| PE → PA / PO | Creation on behalf of producer or origin requiring explicit acceptance | Acopiador / operator | States PA/PO indicate that the counter‑party must accept the CPE.[^2][^27] |
| PA / PO → AC | Acceptance via web portal | Producer or origin plant owner | Handled through ARCA UI, not by WSCPE client.[^27][^16] |
| AC → CF | `confirmarArriboCPE` | Destination operator (CUIT destino) | Sets arrival datetime, marks CF.[^9][^7] |
| CF → DD | `descargadoDestinoCPE` | Destination operator | Indicates physical unloading; CPEDG docs note “Descarga en destino” option becomes available when CPE is vencida.[^12][^11] |
| DD → CN | `confirmacionDefinitivaCPEAutomotor` | Destination operator | Sends final weights, closes CTG.[^9] |
| AC/CF/DD → RE | `rechazoCPE` | Destination | Used when grain is rejected; may be combined with regreso a origen.[^9][^10] |
| AC/CF → AN | `anularCPE` | Origin (solicitante) or producer | Allowed if truck has not effectively used CPE; details in business rules annex.[^1][^10] |
| PA → AP | Cancellation by producer | Producer (via ARCA UI) | Cancels a pending acceptance CPE.[^2][^27] |
| Any “active” → CO | `informarContingencia` | Any interviniente with access | Opens a contingency record.[^1] |
| CO → AC | `cierreContingencia` | Same actor | Returns to AC status after resolving contingency.[^1] |
| AC/CF/CO → (expired) | Time passes beyond validity | System | UI shows “Vencida”; some operations (e.g. “Descarga en destino” for CPEDG) only enabled after expiry.[^3][^11] |
| Various → DE/IN | Administrative actions | ARCA | E.g. sanctions via SISA risk or plant inactivation.[^5][^6] |

For DB/state machine, represent **state + timestamps + reason codes** (anulación, rechazo, contingencia) and keep a **state history table** to reconstruct flows.

### Timeout / auto‑expiration rules

- **Validity:** grain CPE automotor = **5 days**, ferro = **30 days**; both may be extended via contingencies.[^19][^3]
- After expiry, the CPE **cannot be used for new movements**; some flows (e.g. CPEDG “Descarga en Destino”) explicitly require the CPE to be in vencida condition to let the issuer close it without weights.[^11]
- CTG regulations for legacy CTG also treat **vencidos** as CTG no longer counted in “vigentes” for a vehicle’s allowed total weight.[^17]

## Participant roles and permissions

Roles are primarily defined by which CUIT is placed in each interviniente field and by who calls which WSCPE method.[^3][^4][^16]

### Remitente comercial (incl. productor remitente)

Capabilities (through CUIT solicitante or specific interviniente fields):[^14][^4][^16]

- **Emit CPE**: Populate all solicitation fields and call `autorizarCPE…` as CUIT solicitante.
- **Modify CPE** (before use): `modificarCPEAutomotor` / `modificacionIntervinientesCPEAutomotor` for corrections where business rules allow.[^1]
- **Anular CPE**: `anularCPE` while in AC/PE and before arrival or within allowed window; producer can also use AP path when CPE is pending acceptance (PA).[^27][^2]
- **View and consult**: Any interviniente can use consult methods to see full CPE data and states via portal or WS.[^3][^1]

DB‑wise, treat the Remitente as the **issuer/owner** of the document in your tables.

### Destinatario

Destinatario is the **commercial receiver of the grain**; often but not always the plant owner.[^16][^3]

- **Cannot emit CPE** (unless also acting as remitente).
- **Can view and download** any CPE where it is destinatario via ARCA.[^3]
- In many setups the **destination operator** (plant CUIT) handles arrival/descarga/definitive confirmations, not the destinatario per se; but often they coincide.[^7][^16]

You may want a distinction in your ERP between the **operating entity (Destino CUIT)** and the **commercial recipient (Destinatario CUIT)**.

### Intermediario / brokers

Intermediaries are encoded in the intervinientes CUITs (corredor, canjeador, etc.).[^4][^16]

- They can **appear as remitente comercial** (venta primaria/ secundaria) or as **broker CUITs**.
- They generally **do not confirm arrival or unloading**; those actions are reserved for plant/destination CUITs.
- They can **consult and monitor** CPE where they are interviniente.[^3]


### Transportista

Transporter is identified only by `cuitTransportista` and its vehicles and drivers.[^7][^4]

- CTG norms and labor rules oblige the CTG/CPE to identify transporter, km and tariff; but transporter **generally does not emit CPE**.[^20][^14]
- Transporters can consult CPE/CTG assigned to them and prove legality at roadside controls via QR/CTG.[^19][^17]
- They do **not** call WSCPE methods directly in most implementations; they act through the shipper’s or plant’s system.


### Destino / plant operator

The destination plant CUIT (Destino) is the main actor after creation:[^11][^7][^9]

- **Confirm Arribo**: Call `confirmarArriboCPE`, moving from AC to CF.
- **Mark Descargado en Destino**: Call `descargadoDestinoCPE`, moving to DD.
- **Confirmación Definitiva**: Call `confirmacionDefinitivaCPEAutomotor`, sending final weights and closing CTG to CN.[^9]
- **Reject CPE**: Call `rechazoCPE` when grain is rejected; optionally trigger regreso a origen.[^10][^9]
- In CPEDG, the **Destino** also controls “Descarga en Destino” actions to free trucks when CPE is vencida.[^11]

In your permissions model, give **Destino CUIT** rights over all **post‑emission state transitions** (arribo, descarga, rechazo, confirmación) for CPE where it is the registered destination.

## Auxiliary data modeling

### Truck and driver identification

From `transporte`:[^13][^15][^4][^7]

- **Transporter**: `cuitTransportista` → FK to `Carrier` table.
- **Vehicle(s)**: `dominio[]` → you may either store a separate `CPEVehicle` table (CPE id, sequence, plate) or a main plate + trailer plates array.
- **Driver**: `cuitChofer` → FK to `Person` (with link to carrier).
- **Regulatory context:** CTG rules require that **total net kg across all CTG “vigentes” for a truck** must not exceed legal max weight; this is validated per vehicle plate.[^17]


### Grain type and estimated weight

- Grain is identified by `codGrano`, which AFIP documents and Finnegans reproduce (e.g. 19=Maíz, 23=Soja, 15=Trigo Pan, plus many legume and “otros granos” codes).[^10][^4]
- Harvest is `cosecha` (4‑digit), correlated with your **campaign** catalog (20‑21 etc.).[^10][^1]
- Estimated gross/tare are in `datosCarga`; final weights live in the definitive confirmation event.[^4][^9]

Design:

- Table `GrainType` with AFIP code, description and whether it’s grain vs legume vs “other”.
- Store both **estimated** and **final** gross/tare in your CPE header; compute net and mermas both locally and read ARCA’s values for reconciliation.


### Origin / destination plant and field identification

Plants are always identified by **CUIT + planta + locality**, and fields by **CUIT + province/locality + RENSPA/GPS**.[^7][^4][^1][^3]

- Use ARCA’s **Consulta de Plantas** and **Consulta de Domicilios por CUIT** methods to populate master tables (`Plant`, `RegisteredAddress`).[^1]
- Under 2026 rules, the plant must be **“Activa” in SISA** or CPE emission is blocked; your system should mirror plant status.[^5][^29][^6]

Your DB should therefore include:

- `Plant` (cuit, planta_code, province, locality, SISA_state, type).
- `Field` (cuit, province, locality, renspa, gps coords).

Link `CPEOrigin` and `CPEDestination` rows to these.

## Multi‑CTG and partial‑load scenarios

### Multiple CTGs per truck

CTG regulations explicitly allow **multiple CTGs on the same truck**, with a constraint:[^30][^17]

- The **sum of net kg of all CTG “vigentes” assigned to the same vehicle** must not exceed the legal maximum weight in traffic law 24.449.[^17]
- A CTG is considered **vigente** until it is **received (confirmed), annulled, rejected or vencido**.[^17]

So in practice:

- **Yes, one truck can carry multiple CPE/CTG in a single trip**, typically when carrying from multiple origins to one or multiple destinations, as long as weight and routing rules are respected.
- Your schema should allow **N CPE per truck per day**, not a 1:1 relation.


### Can one CPE/CTG cover multiple deliveries?

Regulatory texts and CTG practice treat each CPE/CTG as covering **one contract of carriage between one origin and one destination/destinatario**, although you can **change** destination via desvío/regreso methods.[^31][^32][^33][^9]

- If a truck must unload at **two different plants or destinatarios**, operators normally issue **two separate CPE/CTG**, one per segment, or use a **regreso a origen** + new CPE for the second leg.[^27][^10]
- Resolution 2595/2009 and its complements frame Carta de Porte as the unique document for each transport leg; later CPE regulations keep that model (one CPE per leg)..[^33][^14]

For database/state design: **do not model one CPE as having multiple independent deliveries**; instead relate multiple CPEs to the same physical trip if you need that abstraction.

### Partial loads and differences vs estimate

There are two different “partial” notions:

1. **Difference between estimated and actual weights**
    - Handled through **final gross/tare at destination** vs estimated figures; ARCA computes mermas and net.[^20][^10][^9]
    - No new CPE/CTG is needed; you just record the final weights and let the state go to CN.
2. **Partial delivery to different places or a return of remainder**
    - CTG norms provide **regreso a origen** and **desvío** flows: you report that truck returns with grain or diverts to another plant, often resulting in a **new CPE/CTG for the new leg**, leaving the original marked as “desviada” or similar in your ERP.[^27][^10][^9]
    - CPEDG Q\&A clarifies that for derivatives, **“Descarga en Destino”** can be used to free the truck once the CPEDG is vencida, while further movements must be covered by new documents.[^11]

From a modeling standpoint:

- Treat **each physical unloading location** that needs traceability as requiring its **own CPE/CTG instance or leg**, even if the same truck and trip covers several.
- Represent **desvíos/regresos** as **new CPE records** linked back to the original via a parent‑id, copying common data but changing destination/destinatario fields.

***

## How to translate this into an ERP schema and state manager

Given the above, a practical design for your ERP would be:

- **Master tables**: `Party (CUIT)`, `GrainType`, `Plant`, `Field`, `Vehicle`, `Driver`, `TariffReference`, `SISAPlantStatus`.
- **Document tables**:
    - `CPEHeader` – one row per CPE (CPE number, CTG, tipoCP, state, validity, origin/dest ids, intervinientes, estimated weights, links to transport and grain).
    - `CPETransport` – cuitTransportista, main plate, extra plates, driver CUIT, km, tarifa, flags.
    - `CPEStateHistory` – from_state, to_state, action (method), actor_CUIT, timestamp, reason_code.
    - `CPEWeights` – estimated vs final gross/tare/net/mermas and weighbridge references.
- **Events / WS integration tables**: one per WSCPE operation you support (`Autorizar`, `ConfirmarArribo`, `Descargado`, `ConfirmacionDefinitiva`, `Anular`, `Rechazar`, etc.), storing request/response payloads for audit.

For **field‑level precision** (exact max lengths/formats, multiplicities for every nested type) you should:

- Keep the **WSCPE Manual 2.0.x** and its **Table 2 (Tipos de Datos Simples)** and **Table 3 (Tipos de Datos Complejos)** at hand and, ideally, generate your DB schema or validation layer from the **WSDL** at `…/wscpe/services/soap?wsdl`.[^34][^35][^1]
- Use the **AfipSDK `autorizarCPEAutomotor` schema** as a pragmatic example of all creation‑time fields and types, especially for nested objects (origen/productor, transporte, intervinientes).[^13][^4]

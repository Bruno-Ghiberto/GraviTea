# **Technical Specification and Integration Architecture for the ARCA WSCPE Web Service**

## **Executive Architectural Overview**

The integration of enterprise resource planning (ERP) systems with the Argentine tax and customs authority requires robust middleware capable of handling complex cryptographic authentication, rigorous XML schema validation, and strict adherence to shifting regulatory business rules. The Web Service de Carta de Porte Electrónica (WSCPE) represents the digital backbone for traceability in the agricultural supply chain.1 By replacing legacy physical transit documents with cryptographically verifiable electronic waybills, the WSCPE enforces real-time auditing of grain movements across the national territory.

Recently, the administrative transition from the Administración Federal de Ingresos Públicos (AFIP) to the Agencia de Recaudación y Control Aduanero (ARCA) has introduced architectural updates, including DNS-level endpoint aliases and updated WSDL definitions.2 For developers engineering integration layers for *acopiadores* (grain elevators), agricultural producers, and logistics operators, the WSCPE presents specific technical challenges. These include managing the asynchronous state transitions of the Carta de Porte (CPE), differentiating between logistical modalities, navigating undocumented endpoint behaviors, and handling the proprietary Web Service de Autenticación y Autorización (WSAA) protocol.3 This exhaustive technical specification provides a blueprint for constructing a resilient, compliant, and scalable integration with the WSCPE environment, covering cryptographic provisioning, operational methods, XML payload serialization, error state management, and ecosystem best practices.

## **System Topologies and WSDL Endpoint Resolution**

The WSCPE operates within a dual-environment topology. The Homologation environment acts as a testing sandbox where developers can validate XML generation and signature cryptographic procedures without incurring tax liabilities or registering legally binding transit codes. The Production environment handles live data and requires cryptographic certificates explicitly authorized via the governmental portal.

Due to the transition from AFIP to ARCA, legacy and updated endpoints currently co-exist.1 ERP network layers must be configured to gracefully handle DNS resolution across both domains, as hardcoding a single IP address will result in routing failures during infrastructure maintenance windows. Furthermore, the governmental load balancers mandate the use of Transport Layer Security (TLS) version 1.2 or higher, actively dropping handshakes originating from legacy SSLv3 or TLS 1.0/1.1 clients.3

### **Endpoint Catalog**

| Environment | Purpose | WSDL Endpoint URL |
| :---- | :---- | :---- |
| Homologation (AFIP) | Primary Testing | https://cpea-ws.afip.gob.ar/wscpe/services/soap?wsdl 1 |
| Homologation (ARCA) | Secondary Testing | https://cpea-ws.arca.gob.ar/wscpe/services/soap?wsdl 2 |
| Homologation (QA Ext) | Extended Quality Assurance | https://cpea-ws-qaext.afip.gob.ar/wscpe/services/soap?wsdl 5 |
| Production | Live Operations | https://serviciosjava.afip.gob.ar/wscpe/services/soap?wsdl 6 |

Best practices dictate that the ERP's HTTP client should cache the WSDL definition locally rather than fetching it dynamically on every request. Fetching the WSDL for every operation introduces severe DNS resolution latency and exacerbates the risk of connection timeouts during peak harvest seasons when the ARCA infrastructure experiences extreme load.6

## **Cryptographic Authentication: The WSAA Protocol**

Unlike modern RESTful APIs that utilize static API keys or standard OAuth 2.0 flows, the WSCPE relies on the Web Service de Autenticación y Autorización (WSAA).1 The WSAA is a SAML-adjacent, SOAP-based authentication broker that issues short-lived access tokens based on a cryptographically signed Ticket de Requerimiento de Acceso (TRA).

### **X.509 Certificate Provisioning and Service Delegation**

A persistent point of confusion among integration developers is the relationship between the certificates used for electronic invoicing (WSFEv1) and the WSCPE. The infrastructure utilizes the exact same standard of X.509v3 cryptographic certificates (typically RSA 2048-bit) for all web services.9 A separate certificate enrollment process specifically for WSCPE is not strictly required if a valid certificate already exists for the organization.

However, the critical distinction lies in the authorization model known as "Service Delegation". While the X.509 certificate remains identical, the taxpayer must access the *Administrador de Relaciones de Clave Fiscal* portal to explicitly link the existing certificate to the wscpe service.9 If an ERP attempts to use a certificate that has only been delegated for wsfe to request an access ticket for wscpe, the WSAA broker will return a cryptographic authorization fault, blocking access to the agricultural supply chain endpoints.

### **The loginCms Invocation and the Ticket de Requerimiento de Acceso**

The core authentication method is loginCms, which must be invoked against the dedicated WSAA endpoints. The Homologation endpoint for this service is https://wsaahomo.afip.gov.ar/ws/services/LoginCms?WSDL 11, while the Production endpoint is https://wsaa.afip.gov.ar/ws/services/LoginCms?WSDL.10

To execute loginCms successfully, the ERP system must generate a TRA XML document. This document contains three essential nodes: the destination system (the targeted AFIP environment), the generationTime, and the expirationTime. Crucially, to obtain a token valid for the Carta de Porte service, the service name requested within the TRA XML must be strictly formatted as wscpe.9 Requesting wsfe or wsfev1 will yield a token that is entirely invalid for the WSCPE endpoints.

Once the TRA XML is constructed, it must be encapsulated within a PKCS\#7 / Cryptographic Message Syntax (CMS) structure, signed using the private key corresponding to the X.509 certificate, and encoded into Base64 format. This Base64 string is passed as the sole argument to the in0 parameter of the loginCms SOAP operation.11

### **Rate Limits, Throttling, and Token Caching**

The governmental infrastructure enforces unwritten but aggressive rate limits on the WSAA service to prevent brute-force attacks and mitigate infrastructure strain.13 A critical architectural mandate for any ERP integration is the implementation of a robust token caching layer.10

The Ticket de Acceso (TA) and the Cryptographic Sign returned by a successful loginCms invocation remain valid for a window of 12 to 24 hours.9 ERP systems must serialize these credentials into a secure storage medium—such as a Redis cache, an in-memory datastore, or a relational database table—and append them to every subsequent WSCPE request.1 Requesting a new token from the WSAA for every individual Carta de Porte generation is an implementation anti-pattern that will quickly trigger IP-based throttling. When throttled, the AFIP firewall will either drop the TCP connections entirely or return HTTP 500 Internal Server Errors, severely disrupting the logistics operations of the facility.6

## **Logistical Modalities: Automotor versus Ferroviaria**

The WSCPE encapsulates highly specific Argentine agricultural regulations, differentiating primarily between the logistical modalities of transport.1 ERP business logic must explicitly branch depending on whether the transport is occurring via truck (CPE Automotor) or via train (CPE Ferroviaria), as the underlying state machines and legal validity periods vary drastically.15

For an *acopiador* (a primary grain gathering facility), understanding these differences is paramount. *Acopiadores* handle approximately half of the 344 grain gathering plants in the country and are the central nodes routing grain from producers to export ports.16

### **Distinctions and Validity Periods**

| Feature Category | CPE Automotor (Truck Transport) | CPE Ferroviaria (Rail Transport) |
| :---- | :---- | :---- |
| **Logistical Context** | Utilized for point-to-point, highly granular routing via highways. | Utilized for bulk, aggregated transport via the national rail network. |
| **Legal Validity Period** | Maximum validity of 5 days from the time of authorization.15 | Maximum validity of up to 30 days from authorization.15 |
| **Contingency Management** | Requires rapid "Contingencia" declarations if delayed to avoid expiry.16 | Inherently handles longer delays; contingencies extend the 30-day window. |
| **Relevance to Acopiadores** | Primary modality for dispatching grain to ports and receiving from local farms. | Secondary modality, primarily relevant only for massive inland terminal operators. |

When an *acopiador* acts as the origin point, shipping harvested soy or corn to an export terminal, the ERP will almost exclusively utilize the CPE Automotor schema.15 Because this document expires in precisely 5 days, the ERP must actively monitor the state of the active CPEs. If a truck breaks down or is delayed by a port strike, the ERP must feature an interface allowing the logistics manager to invoke a contingency state, transitioning the document to "Activa con contingencia declarada".16 Failure to implement this lifecycle management results in the expiration of the CTG (Código de Trazabilidad de Granos), legally stranding the cargo on the highway and subjecting the *acopiador* to severe fines by transit inspectors.

### **The "Flete Corto" Workflow for Acopiadores**

The WSCPE logic incorporates a specialized asynchronous flow known as "Flete Corto" (Short Freight), utilized specifically when moving grain from a harvest field directly to a local *acopio*.4 In this scenario, the producer or the *acopiador* can generate the CPE Flete Corto in a "Borrador" (Draft) state.

The system allows the producer to electronically accept the pending CPE up to 72 hours before the physical transfer begins.4 An enterprise-grade integration for an *acopiador* must implement background job processors that continually poll the WSCPE endpoints to detect and automatically ingest incoming, accepted Flete Corto documents. This ensures that the facility's weighbridge software has the CTG data pre-loaded, facilitating rapid validation the moment the truck arrives at the facility gates.

## **Core Operational Methods and Required Input Parameters**

The WSCPE service interface exposes a highly granular set of SOAP operations designed to track the physical movement of agricultural commodities through every state transition.1 Developers must implement exact mappings between the ERP's internal data models and the complex, nested requirements of the WSCPE schemas.5

### **Catalog of WSCPE Methods**

| Method Name | Operational Context and Purpose |
| :---- | :---- |
| solicitarCPEAutomotor | Generates a new Carta de Porte for truck transport and issues the CTG number. |
| consultarCPEAutomotor | Retrieves the current state machine status and metadata of a specific, existing CPE. |
| confirmarArriboCPE | Registers the physical arrival of the transport at the destination facility. |
| confirmarDescargaCPE | Confirms the unloading of the grain, registers the final weight, and concludes the CTG lifecycle. |
| anularCPE | Cancels a CPE entirely, provided the transport has not yet physically commenced. |
| rechazoCPE | Allows the destination facility to reject an arrived CPE due to quality issues or misrouting. |
| consultarRenspa | Validates the sanitary registration polygon of the origin producer (added in WSCPE v2.0.6).17 |

### **Detailed Parameter Requirements per Operation**

The invocation of each method requires specific data payloads wrapped in strict XML canonicalization. The parameters detailed below represent the mandatory fields required to pass the schema validation rules defined by the ARCA infrastructure.

For the solicitarCPEAutomotor method, the ERP must construct a massive payload detailing every commercial and logistical aspect of the trip. Required parameters include the cuitSolicitante (the entity generating the document), the cuitOrigen and cuitDestino (defining the endpoints of the route), and the nroRenspa (the sanitary registration number of the field where the grain was harvested, heavily enforced as of version 2.0.6 17). Furthermore, the datosCarga node requires the specific codGrano (e.g., the numerical code for Soy), the cosecha (harvest year), and the pesoBruto (estimated gross weight). The datosTransporte node must rigidly specify the patente (truck license plate), the trailer plate, and the driver's CUIT.

Upon the physical arrival of the truck at the destination, the ERP must immediately trigger the confirmarArriboCPE method.4 This operation requires a smaller subset of parameters, acting purely as a state transition trigger. The essential inputs are the nroCTG (the unique tracing identifier returned during solicitation), the cuitDestino (to prove the entity confirming is the authorized recipient), the fechaArribo (a strict ISO 8601 timestamp of arrival), and the kmRecorridos (the actual kilometers driven, which are audited against the origin-destination geo-coordinates).

Following the physical weighing and quality analysis of the grain, the *acopiador* utilizes the confirmarDescargaCPE method. This requires the nroCTG, the precise pesoDescarga (the actual scale weight which may differ slightly from the origin weight), and the cuitDestinatario (the ultimate commercial owner of the grain, which may differ from the physical destination CUIT in complex trading scenarios).

If a truck breaks down prior to departing the origin, or if a data entry error is detected, the anularCPE method is utilized.5 This requires only the nroCTG and a structured motivoAnulacion (cancellation reason code). Conversely, if the truck arrives but the grain fails quality inspections (e.g., excessively high moisture content), the destination triggers rechazoCPE, requiring the nroCTG and a detailed rejection taxonomy code.7

Finally, for auditing and validation purposes, the consultarCPEAutomotor method can be invoked by passing either the nroCTG directly, or by passing the vehicle's patente to retrieve the currently active waybill for that specific truck.4

## **Comprehensive XML Schema Serialization and Integration Flow**

The WSCPE communication strictly adheres to the SOAP 1.2 protocol.7 When constructing the soapenv:Envelope, developers must place the authentication token and signature within a dedicated auth block inside the method's request payload, rather than utilizing standard WS-Security headers within the soapenv:Header.1 This structural idiosyncrasy often causes failures for developers relying on auto-generated SOAP clients that default to standard header-based authentication.

To illustrate the technical reality of the integration, the following sections detail the end-to-end XML lifecycle for a typical grain transport operation: the movement of Soy from a local producer directly to an *acopio* \[Prompt Point 9\].

### **Phase 1: Solicitation and Generation (solicitarCPEAutomotor)**

Prior to the truck's departure from the farm, the origin's ERP compiles the logistical data and requests authorization from the WSCPE. The namespace prefix wsc must precisely match the defined URI https://serviciosjava.afip.gob.ar/wscpe/. The grain code 14 represents Soy, and the payload models a 30,000 kg shipment.

XML

\<soapenv:Envelope xmlns:soapenv\="http://schemas.xmlsoap.org/soap/envelope/" xmlns:wsc\="https://serviciosjava.afip.gob.ar/wscpe/"\>  
   \<soapenv:Header/\>  
   \<soapenv:Body\>  
      \<wsc:solicitarCPEAutomotorRequest\>  
         \<auth\>  
            \<token\>PD94bWwgdmVyc2lvbj0iMS4wIiBlb...\</token\>  
            \<sign\>aB3dE...==\</sign\>  
            \<cuitRepresentada\>20111111112\</cuitRepresentada\>  
         \</auth\>  
         \<cpe\>  
            \<cuitSolicitante\>20111111112\</cuitSolicitante\>  
            \<cuitDestino\>30222222223\</cuitDestino\>  
            \<cuitDestinatario\>30222222223\</cuitDestinatario\>  
            \<nroRenspa\>123.456.789.0\</nroRenspa\>  
            \<datosCarga\>  
               \<codGrano\>14\</codGrano\>  
               \<cosecha\>2324\</cosecha\>

While the truck is in transit, highway patrol authorities or the destination *acopio* may query the status of the CTG to ensure it has not been annulled or expired.

Upon reaching the weighbridge of the *acopio*, the facility's ERP must lock the document to prevent the truck from being diverted to another location. This is achieved via the confirmation of arrival.7

Once the Soy is analyzed for moisture content, foreign matter, and precise scale weight, the *acopio* triggers the final discharge event. The net weight measured at the destination dictates the final commercial liquidation of the grain.

   \<soapenv:Body\>  
      \<wsc:confirmarDescargaCPERequest\>  
         \<auth\>  
            \<token\>PD94bWwgdmVyc2lvbj0iMS4wIiBlb...\</token\>  
            \<sign\>aB3dE...==\</sign\>  
            \<cuitRepresentada\>30222222223\</cuitRepresentada\>  
         \</auth\>  
         \<cpe\>  
            \<nroCTG\>987654321012\</nroCTG\>

\</soapenv:Envelope\>

The response permanently closes the CTG lifecycle, setting the state to DESCARGADA, allowing the commercial and tax settlement algorithms to proceed based on the 29850 kg final weight.

## **Diagnostics, Exception Handling, and Error Codes**

Integration resilience in the ARCA environment depends heavily on comprehensive exception handling. The WSCPE provides structured error arrays within the SOAP response payload, allowing the ERP to parse the fault and present actionable feedback to the logistics operators.17 However, developers must also architect defenses against transport-layer anomalies and undocumented infrastructural behavior.

### **Systematic Review of Error Codes and Rejections**

AFIP error codes are strictly numeric and map to complex business rule violations.18 When an operation fails, the \<errores\> array within the response will populate with one or more \<codigo\> and \<descripcion\> pairs.17 The following table categorizes the most frequent rejection reasons encountered by developers building WSCPE clients.

| Error Code | Categorization | Technical Meaning and Resolution Strategy |
| :---- | :---- | :---- |
| **2073 / 2074** | Sanitary Compliance | Related directly to RENSPA (Registro Nacional Sanitario de Productores Agropecuarios) validation failures.17 The ERP must ensure that the agricultural origin polygon is legally registered to the CUIT issuing the grain. If the RENSPA is expired, or if the CUIT attempting to solicit the CPE does not hold a valid lease or ownership over that RENSPA, the payload is immediately rejected. |
| **2243 \- 2247** | Geospatial and Role Consistency | These codes represent internal consistency failures regarding commercial roles or geolocation data, introduced heavily in WSCPE versions 2.0.6 and later.17 This often occurs when the cuitDestino is registered in a province that mathematically contradicts the declared kmRecorridos or route mapping. |
| **Various** | CUIT Invalidations | If the cuitDestino or cuitSolicitante is suspended by ARCA due to unpaid taxes, missing declarations, or severe compliance issues, the CTG generation is halted. Robust ERP systems must implement a pre-flight compliance check utilizing the WS-SR-Padron (Taxpayer Registry) service 20 to verify destination CUIT validity before constructing the WSCPE payload. |
| **Various** | Weight Tolerance Mismatches | During the confirmarDescargaCPE operation, the destination reports the actual physical weight received. If the mathematical variance between the origin pesoBruto and the destination pesoDescarga exceeds the statutory tolerance limit (typically around 4% for certain grains), the automated discharge may fail or be flagged, requiring manual administrative intervention via the ARCA portal. |
| **3051** | Legacy Artifacts | Some older middleware frameworks and governmental FAQs reference Error 3051 or "no disk space" issues.23 These are artifacts of the obsolete SIAP (Sistema Integrado de Aplicaciones) desktop software. Modern REST/SOAP API integrations bypassing the local SIAP executables entirely will not encounter these disk-level errors, though they remain heavily documented in legacy forums.23 |

### **Navigating Infrastructure Faults and HTTP 500 Errors**

A notorious, documented edge case within the AFIP developer ecosystem is the frequent occurrence of HTTP 500 (Internal Server Error) status codes.6 As reported extensively in developer forums, an HTTP 500 received from the autorizarCPEAutomotor endpoint does not indicate an invalid XML schema. If the XML schema were invalid, the AFIP parsers would return an HTTP 200 OK containing a SOAP Fault node specifying "Error en la validacion del esquema XML".6

Instead, HTTP 500 codes indicate an upstream, catastrophic failure within ARCA's internal middleware, such as a database table lock timeout, an inaccessible internal microservice, or load-balancer desynchronization.13

This presents a critical architectural risk. Because an HTTP 500 might occur *after* the internal ARCA database has successfully generated and stored the CTG, but *before* the SOAP response is successfully transmitted back over the network to the client, blindly retrying the solicitarCPEAutomotor payload is dangerous. A blind retry mechanism could result in the generation of duplicate waybills, obligating the producer to deliver twice the physical volume of grain and artificially inflating their tax liabilities.

To mitigate this, ERP systems must implement sophisticated idempotency mechanisms and exponential backoff retry logic. When recovering from an HTTP 500, the system should first invoke the consultarCPEAutomotor method, querying active CTGs associated with the specific vehicle license plate (patente) or driver for that specific date.17 Only if the query confirms that no CTG exists in the active state should the primary generation request be safely re-transmitted.

## **Ecosystem Abstractions, Middleware, and Known Edge Cases**

Developing the cryptographic signatures, handling Base64 CMS structures, and managing XML namespace canonicalization from scratch is highly error-prone. The Argentine developer community has iteratively established several robust open-source wrappers that abstract the SOAP/XML complexities into native objects for high-level languages like Python, JavaScript, and PHP.24

### **Python Implementations and Legacy Bindings**

For enterprise systems built upon Python technology stacks, such as Odoo or Tryton, the PyAfipWs library represents the industry standard middleware.25 Maintained under a software libre model, PyAfipWs provides a dedicated, highly optimized wscpe.py module.25 It handles the CMS cryptographic signing natively via OpenSSL bindings, fully abstracting the WSCPE operational methods into simple class methods.

Furthermore, PyAfipWs provides critical compatibility layers, exposing these Python methods to legacy enterprise languages such as C\#, Java, Visual FoxPro, Delphi, and SAP ABAP via Windows COM interfaces or dynamically linked libraries (DLLs).9 This allows decades-old terminal systems at *acopios* to communicate seamlessly with modern TLS 1.2 ARCA endpoints.

An alternative architectural approach is found in the python-afip package, which targets Python 3 specifically.20 This package attempts to provide a cleaner, "one-function-one-package" abstraction layer, avoiding the complexities of raw SOAP entirely for the end-developer, and providing more natural data structures instead of deeply nested XML dictionaries.20

### **JavaScript and Node.js Integrations**

For modern cloud-native ERPs, Next.js applications, or serverless AWS Lambda microservices, JavaScript and TypeScript libraries such as afip.js provide equivalent structural wrappers.28

When utilizing JavaScript to construct SOAP requests manually without a dedicated library 30, developers must exercise extreme caution regarding XML canonicalization. JavaScript's native string handling and template literals can inadvertently introduce trailing spaces, invisible carriage returns, or alter the encoding format of the Base64 signed payload. ARCA's strict XML parsers will instantaneously reject loginCms or wscpe requests if the payload hash does not perfectly match the cryptographic signature due to these formatting discrepancies. Utilizing established SDKs like afip.js or specialized API proxy wrappers like tusfacturas 29 mitigates these serialization risks entirely.

### **Undocumented Behaviors and Asynchronous Lags**

Analysis of GitHub issue trackers, AFIP developer forums, and Stack Overflow discussions reveals several undocumented behaviors that integration architects must actively program around:

The WSCPE parser is uniquely unforgiving regarding XML namespace enforcement. While standard, compliant SOAP parsers are generally prefix-agnostic as long as the underlying URI matches, the AFIP WSCPE parser frequently hard-fails if the request body does not precisely utilize the prefix conventions documented in their internal manuals.6 Developers must ensure that custom XML serializers strictly adhere to the expected prefix strings (e.g., wsc or tns).

A common source of authentication failure is clock drift vulnerability. The WSAA loginCms method strictly validates the generationTime embedded within the TRA against AFIP's internal Network Time Protocol (NTP) servers. If the ERP server's local clock drifts by more than 5 minutes, the TRA will be rejected as mathematically invalid, regardless of cryptographic correctness. Implementing an aggressive NTP synchronization daemon (such as chronyd) on the ERP application servers is a mandatory infrastructural requirement.

Finally, logistical friction often arises from internal database desynchronization regarding the SMS verification systems. AFIP provides an automated SMS service (accessed by texting "CPE" followed by the document number to 2347\) for transit authorities and highway police to instantly verify the validity of waybills.4 However, there is frequently a documented lag of several minutes between a successful solicitarCPEAutomotor SOAP response reaching the ERP and the new CTG propagating into the SMS query database. Transport operators and truck drivers must be procedurally advised to wait 5 to 10 minutes after generation before departing the facility to avoid false-positive detentions at highway checkpoints, where police might temporarily view the newly generated CTG as non-existent.

## **Synthesis of the Architectural Imperative**

The implementation of the ARCA Web Service de Carta de Porte Electrónica demands an integration layer that transcends simple data transmission. It requires the programmatic encapsulation of complex national logistics, tax legislation, and agricultural sanitary regulations. By securely managing the WSAA cryptographic lifecycle to prevent throttling, implementing defensive state-machine recovery around HTTP 500 faults, deeply understanding the temporal distinctions between Automotor and Ferroviaria logistical modalities, and leveraging established middleware ecosystems to ensure strict XML canonicalization, ERP engineers can construct systems capable of seamless, uninterrupted operation across the Argentine agricultural supply chain.

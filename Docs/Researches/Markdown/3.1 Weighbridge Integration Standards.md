# Weighbridge Systems at Argentine Acopios: Integration Guide for ERP Software

## Executive Summary

This report provides a technical reference for integrating ERP software with weighbridge (báscula/balanza) systems used by acopiadores (grain storage operators) in Argentina. It covers the dominant equipment brands, communication protocols and data formats, software ecosystems, certification requirements, and the operational weighing workflow. The Argentine weighbridge market is dominated by domestic manufacturers based in Santa Fe and Córdoba, virtually all of which communicate via RS-232 serial with ASCII-encoded weight data — though Modbus RTU and Ethernet bridging are increasingly available. For an ERP integration, the primary engineering task is parsing vendor-specific ASCII serial frames, typically at 9600 baud, 8N1.

***

## Communication Protocols

### RS-232 Serial: The Universal Baseline

RS-232 is the de facto standard communication interface across virtually every weighbridge indicator used in Argentine acopios. All major Argentine indicator brands (Sipel, GaMa, Systel) include an RS-232 port as standard equipment.[^25][^19][^17]

**Typical serial parameters:**

| Parameter | Common Values |
|---|---|
| Baud rate | 9600 bps (most common default); 1200, 2400, 4800, 19200, 38400 also configurable[^26][^17] |
| Data bits | 8 |
| Parity | None |
| Stop bits | 1 |
| Connector | DB-9 male (plastic enclosures) or terminal block (stainless steel enclosures) |
| Max distance | 15 meters[^27] |

### USB Serial Emulation

Modern PCs lack native RS-232 ports, so USB-to-RS232 adapters are extremely common. KYASERV and Sipel both sell OEM USB-RS232 adapters specifically designed for scale connectivity. These create a virtual COM port that your ERP application reads identically to a physical serial port. Sipel's Orion indicator is also available with an optional native USB port that presents as a virtual serial device.[^27][^25]

### Modbus RTU / Modbus ASCII

The **Sipel Orion** supports full Modbus RTU and Modbus ASCII over both RS-232 (single-slave, 15m max) and RS-485 (multi-slave, 1200m max). This is the most structured and integration-friendly protocol available:[^27]

- **Supported functions:** 03h (Read Holding Registers), 06h (Write Single Register), 10h (Write Multiple Registers)
- **Memory map:** Address 0 = Gross weight (2 registers, 32-bit signed integer), Address 2 = Tare, Address 4 = Net weight, Address 6 = Flags/Status[^27]
- **Configuration:** Slave ID 0–99, baud 4800–38400, RTU mode (8-N-1) or ASCII mode (7-N-2)[^27]

Some generic indicators from Chinese manufacturers (e.g., XK3190-C8+, TDA-08A) also support Modbus RTU, commonly at 9600 baud.[^28][^29]

### Ethernet/TCP-IP

No major Argentine indicator natively includes an Ethernet port in standard configuration, but RS-232-to-Ethernet converter modules are readily available:

- **KYASERV RS232-Ethernet module:** Converts full-duplex RS232 data to UDP-TCP/IP over wired Ethernet, making the scale a node on the plant network[^30][^25]
- **KYASERV RS232-WiFi module:** Same concept over wireless, useful for crane scales or mobile setups[^25]
- **Sipel external modules:** RS232-to-TCP/IP (Ethernet), RS485-to-Modbus TCP, RS485-to-Profibus, and wireless Zigbee modules are listed as accessories for the Orion indicator[^16]
- **Mettler-Toledo IND780:** Natively supports Ethernet/IP, Profinet, Modbus TCP, DeviceNet, and ControlNet[^23]

The KYASERV converter is particularly noteworthy for ERP integration: it can redirect serial data from **any brand/model** of scale to a network destination, a virtual serial port, or even a disk file — and it reformats the data string to match whatever format the receiving software expects.[^30]

### Bluetooth / WiFi / 4G

Traditional weighbridge indicators do not include Bluetooth. WiFi connectivity is achieved through RS232-WiFi bridge modules rather than native indicator hardware. The notable exception is the **Corvus AGDP** system for tolvas (grain carts), which uses 4G cellular and GPS for cloud-connected real-time weight monitoring from the field, including remote calibration and automatic report generation.[^31][^32][^33][^25]

## Data Formats

Each manufacturer uses a proprietary ASCII frame format. There is no single universal standard like OIML R76 mandating a specific data output format at the serial level. Below are the documented formats for the most common indicators.

### Sipel Orion — Multiple Selectable Formats

The Orion indicator offers several configurable output formats via the FI parameter (when configured for PC output, RE=PC):[^34]

| FI Value | Format |
|---|---|
| **0** | `<STX><MTO><E/S><Neto(8)><CR><LF><ETX>` |
| **1** | `<STX><Id(10)><CR><LF><Neto(10)><CR><LF><Flags(10)><CR><LF><ETX>` |
| **2** | `<STX><Id(10)><CR><LF><Bruto(10)><CR><LF><Tara(10)><CR><LF><Neto(10)><CR><LF><Flags(10)><CR><LF><ETX>` |
| **3** | `<SOH><Formato(10)><CR><LF><STX><Neto(10)><CR><LF><ETX><Capacidad(10)><CR><LF><EOT>` |
| **4** | `<STX><Neto(9)><0x7C><Estado(1)><CR>` |
| **5** | User-defined (via Lego Orion software) |

Transmission can be **continuous** (TI=CON) or **manual/on-demand** (TI=MAN), depending on the indicator configuration. Status flags indicate: negative display, center of zero, motion/instability, net mode, and error conditions.[^27]

### GaMa A12 — Continuous Stream

The A12 transmits continuously in the format:[^26][^35]

```
SPPPPPP<CR>
```

Where:
- **S** = Status byte (1 byte, ASCII-encoded flags)
- **P** = Weight value in ASCII (6 digits, as shown on display)
- **CR** = Carriage return (0x0D)

Baud rate is selectable: 1200 (default), 2400, 4800, or 9600 bps, always 8-N-1. The status byte encodes gross/net mode, equilibrium/stability, sign, and out-of-range conditions. For example, status byte `D` = gross weight positive and greater than zero; `E` = net weight positive and greater than zero; `F` = center of zero without tare.[^35][^17][^26]

### Systel — Command/Response (Polling)

Systel uses a **request/response** protocol rather than continuous streaming:[^19]

- **Request stable weight:** Send byte `$05` (ENQ). Response: `$02` + 6/7 bytes ASCII weight + `$03` + XOR checksum (9 or 10 bytes total)
- **Request weight with stability flag:** Send `$07` (or `$07 $07`). Response includes an `e` (stable) or `i` (unstable) byte[^19]
- **Torrey compatibility mode:** Send ASCII `P`. Response: `<CR>` + signed weight ASCII[^19]
- **CAS compatibility mode:** Send ASCII `W`. Response: `<STX>` + weight digits + `<CR>`[^19]

The weight is transmitted exactly as shown on the display, including decimal position. Systel provides a Visual Basic source code sample ("Prueba Protocolo Systel") for developers to test the communication.[^19]

### Modbus (Sipel Orion)

When using Modbus, the data is structured as standard Modbus registers rather than ASCII strings. Weight values are 32-bit signed integers (two registers each), without a decimal point — the decimal position must be known from the indicator configuration.[^27]

### Integration Recommendation

For ERP integration, the recommended approach is:

1. **Primary:** Use Modbus RTU (Sipel Orion) or the command/response protocol (Systel) — both allow the ERP to poll for weight on demand rather than parsing a continuous stream.
2. **Fallback:** Parse continuous ASCII streams (GaMa A12, Sipel FI=0) using frame delimiters (STX/ETX or CR/LF).
3. **Network:** Use a KYASERV RS232-Ethernet bridge to make the indicator accessible via TCP/IP, allowing your ERP to connect from anywhere on the LAN.[^30]

## Software APIs and Cloud Connectivity

### Standalone Weighing Software

Most Argentine weighbridge installations use dedicated weighing software that sits between the indicator and any ERP system:

- **Sipel PESAR:** General-purpose capture software supporting SQL Server/Compact Edition databases; connects via RS232, USB, and TCP/IP; supports Modbus series and Modbus TCP/IP; exports to Excel; barcode reader input; compatible with Sipel and Ohaus indicators[^24]
- **Sipel GALIL:** Purpose-built for truck weighing with vehicle/driver registries, 1 or 2 scales, TCP/IP communication, SQL Server option, and AFIP RG 3890 compliance for ticket generation[^36]
- **Básculas Casilda v4.0:** Visual FoxPro-based, tracks clients/suppliers/carriers/trucks, exports ASCII or Excel, complies with AFIP RG 271/98 for grain operations[^37]
- **KYASERV Converter Module:** A middleware layer that captures the serial weight string from any brand of scale, converts it to any format, and retransmits to a serial port, network destination (UDP), virtual COM port, or disk file — enabling legacy software to work with any scale brand[^30]

### Cloud-Connected Systems

- **Corvus AGDP:** Cloud-native system for tolvas (grain carts) with 4G/GPS connectivity, real-time weight visualization, HD cameras with night vision, remote calibration, automatic report generation, and in-field carta de porte creation. Integrated into Básculas Magris product line[^32][^33][^31]
- **Cachapuz SmartWeigh:** Industry 4.0 weighing management platform with automated access control, ERP integration, vehicle identification, and complete audit trails. More common in European/industrial installations than typical Argentine acopios[^15]
- **Systel ONE:** Integrates Systel weighing hardware with Odoo ERP (v18.3+), offering cloud-based sales, stock, pricing, and customer management with automated weighing-to-billing workflows[^18]

### API Availability

No Argentine weighbridge indicator manufacturer currently offers a REST API or modern web API as a standard feature. The integration pathway is either:

1. **Serial/Modbus** direct connection from your ERP to the indicator
2. **Database sharing** with Sipel PESAR/GALIL (SQL Server) or exporting data via CSV/Excel
3. **Middleware** such as the KYASERV converter to bridge serial data to your preferred consumption method (network socket, file, virtual port)
4. **Cloud APIs** are only available through the Corvus AGDP platform for field tolva applications[^32]

## Certification and Legal Metrology

### Regulatory Framework

Argentine legal metrology for weighing instruments is governed by:[^38][^39]

- **Ley 19.511** (SIMELA — Sistema Métrico Legal Argentino): The foundational law establishing that all measuring instruments used in commercial transactions must comply with legal metrology requirements[^38]
- **Decreto 788/2003:** Assigns INTI as the entity responsible for model approval, primitive verification, and periodic verification of regulated instruments[^39]
- **Resolución 48/2003:** General criteria for legal metrology[^11]
- **Resolución 49/2003:** Procedures for periodic verifications, primitive verifications, and model approvals[^11]
- **Resolución 19/2004:** Requirements for manufacturers to undergo INTI audits for declarations of conformity[^39]

### Verification Requirements

Any weighbridge used for commercial grain transactions at an acopio is a regulated instrument and must undergo:[^9][^38]

- **Model Approval (Aprobación de Modelo):** The indicator/scale model itself must be approved by INTI before it can be sold for commercial use. The GaMa A12, for example, is approved with code BF.60-2181.[^12]
- **Primitive Verification (Verificación Primitiva):** Initial verification upon installation, using certified test weights (Datta, for example, maintains over 50,000 kg of certified pattern weights).[^9]
- **Periodic Verification (Verificación Periódica):** Must be performed at regular intervals. KYASERV documentation states every **two years**, while La Torre Pesaje describes it as **annual** — the frequency may depend on the specific instrument class and provincial requirements. This verification is audited by an accredited laboratory (INTI or OAA-accredited private labs).[^40][^38]

### Major Regulatory Change (2025–2026)

INTI Resolution 213/2025 announced that INTI will **cease providing direct certification and verification services** nationwide, delegating these functions to OAA-accredited (Organismo Argentino de Acreditación) private laboratories. The implementation timeline is:[^41]

- **AMBA (Greater Buenos Aires):** From January 31, 2026[^41]
- **Most provinces** (including Misiones, Chaco, Entre Ríos, etc.): From April 30, 2026[^41]
- **Córdoba, Mendoza, San Juan, San Luis, Santa Fe:** From June 30, 2026[^41]

This means that in the grain belt provinces (Córdoba, Santa Fe), the transition is still in progress. Existing INTI certifications and ongoing work orders will be honored until completion. Going forward, acopios will need to work with OAA-accredited private laboratories for their periodic verifications.[^41]

### Weighing Accuracy Class

Truck scales in Argentina are classified as **Class III** instruments under OIML standards. Typical capacities range from 30,000 to 80,000 kg, with division sizes (d) of 10 or 20 kg.[^42][^12]

## The Weighing Process at an Acopio

### Standard Two-Weighing Procedure

The grain reception process at a typical acopio follows a well-established sequence:[^43][^44]

1. **Arrival and documentation:** The truck arrives with a Carta de Porte Electrónica (electronic waybill, CPE), which is mandatory for grain transport and must include gross weight, tare, and net kilos.[^45][^46]

2. **Gross weight (Peso Bruto):** The loaded truck drives onto the weighbridge. The operator records the gross weight (truck + grain).[^43]

3. **Sampling (Calado):** Before or after the gross weighing, a probe (calador) extracts grain samples to assess quality parameters (moisture, foreign matter, damaged grain). These determine any commercial discounts (mermas/rebajas).[^43]

4. **Unloading (Descarga):** The truck proceeds to an unloading platform (plataforma volcable) to dump its grain load.

5. **Tare weight (Peso Tara):** The empty truck is weighed again on the weighbridge. The Carta de Porte is finalized at this stage.[^43]

6. **Net weight calculation:** Net = Gross − Tare. This is the billable grain weight before quality discounts.

### Tare Handling Variations

- **Standard:** Tare is measured each trip (most common and legally required for the CPE).[^46]
- **Known tare:** Some operations store a vehicle's tare from a previous weighing and use it for subsequent trips. This is less rigorous but sometimes used for trusted regular carriers.
- **Multiple CPEs per truck:** A truck can carry multiple products with separate Cartas de Porte, but the sum of net kilos plus tare must not exceed the legal maximum weight limit.[^47]

### Automation and Technology

- **License plate recognition (LPR/ANPR):** VisArt is the leading Argentine LPR software, specifically designed for Argentine plate formats. It is used at some weighbridge installations to automatically identify trucks on the scale, reducing manual data entry and preventing fraud.[^48][^49]
- **RFID:** Not widely adopted at Argentine acopios for weighbridge automation, though it is more common in controlled industrial environments.
- **Semaphore/traffic control:** The Sipel Orion indicator has built-in I/O for controlling traffic lights and position barriers at axle-weighing stations. Cachapuz SmartWeigh also includes intelligent positioning and access control.[^15][^27]
- **The workflow remains predominantly manual** at most acopios: a balancero (scale operator) manages the weighing process, enters vehicle/driver data, triggers weight capture, prints tickets, and manages the Carta de Porte documentation.

## ERP Integration Architecture Recommendations

### Protocol Priority for Your ERP

| Priority | Method | When to Use |
|---|---|---|
| **1** | Modbus RTU over RS-232 or RS-485 | Sipel Orion indicators — structured, polled, well-documented register map[^27] |
| **2** | Command/Response ASCII over RS-232 | Systel indicators — send $05/$07, parse response frame[^19] |
| **3** | Continuous ASCII stream parsing | GaMa A12 and other streaming indicators — parse SPPPPPP\<CR\> frames[^26] |
| **4** | TCP/IP via RS232-Ethernet bridge | Any indicator with KYASERV converter — same serial protocol over network socket[^30] |
| **5** | SQL Server database read | When Sipel PESAR/GALIL is installed — read directly from their SQL database[^24][^36] |

### Practical Considerations

- **Plan for multiple protocols.** An acopio may have a Sipel indicator on one scale and a GaMa on another. Your ERP should support at least 2–3 protocol parsers.
- **Handle stability detection.** Never record a weight while the indicator signals motion/instability. Check the stability flag (Sipel MTO byte, GaMa status byte, Systel e/i indicator) before accepting a reading.[^35][^19][^27]
- **USB-to-serial adapters** are the norm on modern PCs. Ensure your software correctly enumerates and connects to virtual COM ports.[^25]
- **Consider RS232-Ethernet bridges** for multi-scale operations. They allow centralized weight capture from a server without running serial cables to each PC.[^30]
- **Carta de Porte integration** is essential. Your ERP should populate the CPE fields (gross, tare, net) directly from the captured weight data to comply with AFIP/SISA requirements.[^45][^46]

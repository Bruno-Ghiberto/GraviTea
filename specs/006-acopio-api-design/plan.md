## Phase 0: Research

### Research Tasks

All domain facts have been gathered from upstream blueprint docs and RAG queries during the `/sc:design` phase. This section consolidates the research findings that resolve endpoint field definitions.

### R1: Romaneo Endpoint Field Sources

**Decision**: All romaneo request/response fields are taken verbatim from Data Model §5.3 (31 fields across 7 groups). No new fields invented.
**Rationale**: The Data Model v1.0 is the single source of truth for all Django models. The API spec exposes these fields through REST endpoints, not creates them.
**Source**: `Docs/Project Blueprint/Data Model & Domain Model.md` §5.3

### R2: State Transition Endpoint Sequencing

**Decision**: The 7-step romaneo lifecycle maps to 6 API state transition endpoints: confirmar-arribo (→ EN_PROCESO), peso-bruto (→ PESADO), analizar (→ ANALIZADO), confirmar (→ CONFORME), tara (captures tare weight), cerrar (→ CERRADO).
**Rationale**: HLD §9.1 ten-step flow defines the physical workflow. The state machine in Data Model §5.3 defines the valid transitions. Tare weight is captured after unloading, between CONFORME and CERRADO.
**Source**: HLD §9.1, Data Model §5.3 state machine

### R3: ARCA Async Call Pattern

**Decision**: Endpoints that trigger ARCA WSCPE calls (confirmar-arribo, cerrar) return HTTP 202 Accepted and enqueue the call to `apps/sync.PendingOperation`. Response includes `pending_operation_id`.
**Rationale**: ADR-030 (Store-and-Forward Queue) mandates that all ARCA calls are asynchronous. The offline-first architecture (ADR-028) requires that romaneo issuance proceeds regardless of ARCA connectivity.
**Source**: ADR-028, ADR-030, HLD §9.1 (step 10 note)

### R4: Producer Account Derived Views

**Decision**: `posicion-consolidada` is a GET-only computed endpoint (SQL aggregation over `ProducerAccount` across all branches), not a stored CRUD resource.
**Rationale**: ADR-013 (Posición Consolidada as Derived View) explicitly governs this pattern. The derived view is always fresh — no cache invalidation needed.
**Source**: ADR-013, Data Model §6.1

### R5: Pagination Strategy Split

**Decision**: Cursor-based pagination for append-only ledgers (AccountMovement, GrainMovement). Page-number pagination for reference data (grain-types, tolerance-tables) and romaneo lists.
**Rationale**: Constitution XIII mandates cursor-based for large datasets. Append-only ledgers grow unboundedly. Reference data and romaneo lists are bounded and benefit from count-aware pagination.
**Source**: Constitution §XIII, ADR-008

### R6: Error Response Format

**Decision**: RFC 7807 Problem Details (`application/problem+json`) with domain-specific extensions: `romaneo_status` for immutability violations, `conflict_strategy` for sync conflicts.
**Rationale**: RFC 7807 is the industry standard for structured HTTP error responses. Domain extensions allow clients to programmatically handle grain-domain-specific errors.
**Source**: FR-012 in spec.md

### R7: Encrypted CUIT Field API Behaviour

**Decision**: API accepts plaintext CUIT in requests. Server encrypts transparently. Filtering by `?producer_cuit=XX` searches the HMAC-SHA256 blind index (equality only). LIKE/range queries on CUIT are not supported.
**Rationale**: ADR-022 (AES-256-GCM with blind index) governs this pattern. The blind index is deterministic, enabling equality search without decrypting all records.
**Source**: ADR-022, Data Model §6.1 (producer_cuit field)

### R8: Phase 2 Endpoint Shapes

**Decision**: Phase 2 endpoints (liquidaciones, facturación) are documented as placeholder URL patterns with HTTP methods and brief descriptions, but WITHOUT full field tables. They are clearly labelled "Phase 2 — Not active in Phase 1 delivery."
**Rationale**: Providing URL shapes now stabilizes the contract for planning purposes. Full field tables are deferred until the Phase 2 specs are written.
**Source**: FR-016 in spec.md, HLD §5.7-5.8
